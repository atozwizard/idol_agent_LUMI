# 에이전트 이슈 생성 대화형 가이드

## 목적
- 신규/기존 작성자가 이슈 생성 절차를 정확히 이해한 상태에서 이슈를 생성하도록 표준 대화 절차를 정의한다.
- 에이전트는 요청 즉시 이슈를 생성하지 않고, 필수 정보 수집과 이해도 확인, 최종 승인 단계를 거친다.

## 적용 범위
- GitHub Issue 생성 요청 전반
- 단일 작성자/복수 작성자 협업 이슈
- 리팩토링, 기능 개발, 버그 수정, 운영성 작업 이슈

## 핵심 원칙
- 이슈 생성은 `즉시 실행`이 아니라 `질문 기반 확인`이 기본이다.
- 사용자가 프로세스를 이해했는지 확인하기 전에는 이슈를 생성하지 않는다.
- 최종 승인을 받기 전에는 `gh issue create`를 실행하지 않는다.
- 협업 이슈는 담당자, 범위, 머지 조건을 명시한다.
- `dev` 안정성을 우선하며, 중간 머지로 `dev`가 깨지는 흐름은 금지한다.

## 표준 프로세스
1. 요청 접수 및 생성 보류 선언
   - 에이전트는 "필수 정보를 확인한 뒤 최종 승인 후 생성"을 먼저 안내한다.
2. 필수 정보 질문
   - 이슈 제목, 목적, 작업 유형, 대상 파일/모듈, 담당자, 브랜치 전략, 완료 기준을 질문한다.
3. 협업/의존성 확인
   - 다중 작성자인지, PR 분리 여부, 단독 머지 시 `dev` 안정성 여부를 확인한다.
4. 초안 제시
   - 에이전트가 제목/본문 초안을 제시하고, 누락/오해 여부를 사용자와 교차 확인한다.
5. 이해도 점검
   - 사용자에게 작업 프로세스(브랜치/PR/머지/종료 규칙)를 1회 재확인 질문으로 점검한다.
6. 최종 승인 요청
   - "이 내용으로 이슈를 생성할까요?"를 명시적으로 질문한다.
7. 생성 실행
   - 승인 후 `gh issue create` 실행, URL 반환, 생성된 메타데이터 확인 결과를 공유한다.

## 필수 질문 세트
- 작업 유형은 무엇인가? (`feat` / `fix` / `refactor` / `etc`)
- 이번 이슈의 목표와 완료 기준은 무엇인가?
- 대상 범위(파일/모듈)는 어디까지인가?
- 작성자는 누구이며, 담당 범위는 어떻게 나눌 것인가?
- 브랜치 전략은 무엇인가? (공용 브랜치 1개 + 단일 PR 권장)
- PR/이슈 연결 규칙은 어떻게 할 것인가? (`Refs` / `Closes`)
- 부모 이슈의 `labels`, `type`, `project`를 하위 이슈에 반영해야 하는가?

## 이해도 점검 질문 예시
- "중간 PR이 단독 머지되면 `dev`가 깨지는 경우, 어떤 전략으로 진행해야 합니까?"
- "최종 이슈 종료 키워드는 어떤 PR에서 사용합니까?"
- "작성자별 작업 분리는 이슈 본문과 sub-issue 중 어디에 명시합니까?"

## 승인 게이트 규칙
- 아래 조건을 모두 만족할 때만 이슈를 생성한다.
  - [ ] 필수 질문 응답 완료
  - [ ] 이슈 제목/본문 초안 사용자 확인 완료
  - [ ] 프로세스 이해도 점검 완료
  - [ ] "생성 진행"에 대한 명시적 승인 획득

## 협업 이슈 권장 규칙
- 기본값: 공용 브랜치 1개 + PR 1개
- 두 PR이 모두 `dev`에 반영되어야 정상 동작하는 경우
  - 첫 PR 단독 머지 금지
  - Draft PR 또는 공용 브랜치 통합 후 단일 PR 머지
- 필요 시 작성자별 sub-issue를 생성하되 과도한 분할은 피한다. (권장: 2개 수준)

## 메타데이터 반영 규칙
- 부모 이슈 메타데이터를 먼저 확인한다. (`gh issue view <번호> --json ...`)
- 가능한 경우 아래 항목을 동일 반영한다.
  - `labels`
  - `assignees`
  - `project` (권한/설정 허용 시)
  - `type` (리포 설정 정책에 따름)
- 도구 제약으로 직접 반영이 어려운 항목은 본문에 명시적으로 기록한다.

## 표준 본문 템플릿
```md
## 배경
-

## 목표
-

## 대상 범위
-

## 작성자별 담당
- 작성자 A:
- 작성자 B:

## 작업 프로세스
1. dev 최신 반영
2. 공용 브랜치 생성
3. A 작업 후 push
4. B 작업 후 push
5. 통합 테스트
6. 단일 PR 생성 및 머지

## 머지/종료 규칙
- 중간 머지 금지 조건:
- 최종 PR에서만 `Closes #<번호>` 사용

## 완료 기준
- [ ]
- [ ]
```

## 실행 예시 (승인 후)
```bash
gh issue create \
  --title "refactor: 예시 제목" \
  --label "refactor" \
  --body "$(cat <<'EOF'
## 배경
- ...
EOF
)"
```

## 체크리스트
- [ ] 질문 기반 확인을 선행했는가?
- [ ] 사용자 이해도 점검을 수행했는가?
- [ ] 최종 승인을 받은 뒤 생성했는가?
- [ ] 생성 후 URL과 반영 메타데이터를 공유했는가?
